# MATLAB: общая модель LLM + HBM для VCU128 openTPU

Модель показывает авторегрессионный inference и его нагрузку на HBM:
чтение весов, вычисления MXU, attention, рост KV-cache, время каждого токена.
Ethernet в модели отсутствует. Не нужны плата, Vivado, Simulink или toolbox.

Есть два режима:

1. **Исполняемый небольшой декодер**: настоящие численные тензоры, INT8 MXU,
   RMSNorm, RoPE, causal attention/GQA, SwiGLU, residual, выходные логиты,
   greedy generation. Случайные веса позволяют исследовать механизм;
   осмысленный текст и tokenizer в этот пример не входят.
2. **Символьный профиль большого декодера**: те же размеры операций и учёт HBM,
   но без размещения тензоров в ОЗУ и без вычисления логитов. Можно быстро
   менять контекст, размер модели, частоты и параметры HBM.

Это LLaMA-подобная архитектура для изучения принципов. У работающих на плате
LFM2.5 и Qwen3.5 есть другие блоки, в том числе hybrid/recurrent attention;
данная модель не воспроизводит их архитектуры и checkpoint.

## Быстрый запуск

Из корня репозитория в MATLAB:

```matlab
addpath('vcu128_otpu/sim/matlab');
test_otpu;
r = run_demo;          % численный inference и графики
profile = run_profile; % большая модель и зависимость от длины контекста
```

Без графики: `r = run_demo([], false);` и `profile = run_profile([], false);`.
Код использует implicit expansion и jsondecode (MATLAB R2016b+).
Непосредственно в MATLAB здесь не проверялся: MATLAB в PATH отсутствует.
Фактически проверен GNU Octave 8.4.0:

```bash
octave --quiet --no-gui --eval \
  "addpath('vcu128_otpu/sim/matlab'); test_otpu; r=run_demo; profile=run_profile;"
```

`out/` игнорируется Git. Численный пример сохраняет `llm_results.mat`,
`llm_trace.csv`, `llm_summary.txt`, `llm_overview.png`. Большой профиль —
`llm_profile.csv`, `llm_profile.mat`, `llm_profile.png`.
В CSV трассы для каждой операции записаны токен, слой, имя, байты чтения/
записи, число операций, оценки времени HBM/вычислений, начало и конец.

## Как устроен один токен

```
ID токена → embedding из HBM
  → [RMSNorm → Q/K/V INT8 → RoPE → запись K/V в HBM
     → чтение KV всего префикса → causal GQA attention → O INT8 → residual
     → RMSNorm → gate/up INT8 → SwiGLU → down INT8 → residual] × layers
  → RMSNorm → INT8 lm_head → logits → argmax → следующий ID
```

На входе — 1-based ID в диапазоне `1…vocab`. Сначала prompt обрабатывается
последовательно, затем следующий токен выбирается по argmax. Prefill здесь
**последовательный**, без пакетного GEMM нескольких позиций. Последний выбранный
токен не обрабатывается повторно, поэтому число обработанных позиций равно
`length(prompt) + generate - 1`. `prefill_s` — оценка времени до первого
сгенерированного ID; время host/tokenizer не учитывается.

GQA делит query heads на группы, использующие один KV head. RoPE применяется
попарно к соседним координатам с позицией `0…max_seq-1`. В KV-cache хранятся
уже повёрнутые K и исходные V как INT8 с FP32-масштабом на токен и KV-голову
(как QST ROW в RTL; в массивах хранится деквантованная копия), отдельно для
каждого слоя. Attention
читает только позиции до текущей включительно. Embedding/output head связаны
исходными весами; на HBM учитываются FP32 embedding и INT8 lm_head со шкалами.

По умолчанию: 2 слоя, hidden=128, intermediate=256, 4 query heads,
2 KV heads, vocab=256, max_seq=64, 8 генерируемых ID. Матрицы создаются
детерминированно по seed. Алгоритм RNG в MATLAB и Octave может различаться;
эталонные JSON-вектора MXU от этого не зависят.

## Изменение параметров

```matlab
c = otpu.config();       % архитектура из target/vcu128.toml
p = otpu.llm_config();
p.layers = 4;
p.hidden = 256;
p.intermediate = 768;
p.heads = 8;
p.kv_heads = 2;
p.max_seq = 128;
p.prompt = [1 5 9 17];
p.generate = 16;
r = run_demo([], true, p, c);

% Большая условная LLM: профиль без выделения весов и вычисления логитов.
p.layers = 24; p.hidden = 1024; p.intermediate = 4096;
p.heads = 16; p.kv_heads = 4; p.vocab = 32000;
q = run_profile([], true, p, c, [1 128 512 2048 8192 32768]);

% Влияние памяти при тех же вычислениях:
c.read_slots = 8;
c.read_latency = 100;
slow = otpu.llm_profile(p,c,[128 2048 8192]);
```

`hidden` и `intermediate` должны быть кратны D=128; head_dim — чётный,
heads кратно kv_heads. Входная размерность одной MM не больше ACT_BLOCKS*D.
KV — INT8 + масштаб (раскладка и байты: `otpu.kv_bytes`), веса только INT8. `llm_init` проверяет вместимость
весов и зарезервированного KV в активные `2*S` канала по 2 GiB. Большой
профиль возвращает `fits_hbm` для каждой длины контекста; точки вне ёмкости
сохраняются для анализа, но не означают исполнимую конфигурацию.
S>1 в оценке означает идеальное разделение выходных строк и памяти; реальное
размещение и компиляция нескольких слайсов не моделируются.

Для пошагового просмотра:

```matlab
[model,state] = otpu.llm_init(p,c);
[logits,state] = otpu.llm_step(1,model,state,c);
[logits,state] = otpu.llm_step(7,model,state,c);
% state.K, state.V — содержимое cache; state.trace — временная трасса
```

## Точность вычислений

INT8 путь воспроизводит подмножество FeSens MXU/QACT/QST, а не обычное
умножение int8 после квантования каждого блока отдельно. Квантователь имеет
FP32 масштаб строки, смещения групп d=0…31, nearest-even и насыщение ±127.
QACT использует группы D/4, QST — D. В одном MM:

```
c[m,n,g] = sum(qA[m,g,:] * qW[n,g,:])
shift = 16 - dA[m,g] - dW[n,floor(g/4)]
acc[m,n] = sum(c * 2^shift) по группам shift >= 0
Y = fp_mul(fp_mul(fp32(acc), Sw), fp_mul(Sa, 2^-16))
```

Группы с отрицательным shift отбрасываются. FP32 операции разделены,
с flush-to-zero после каждого шага, reciprocal реализован по seed/Newton
upstream. Целые суммы через double точны при текущих пределах D/ACT_BLOCKS.
Входы квантователя — конечные FP32. Не реализованы FP4, PAIR, RSC, ACC и
разбиение большого K на несколько инструкций.

RMSNorm, RoPE, softmax и SiLU — математические функции MATLAB с промежуточным
double и возвратом FP32. Они не воспроизводят аппроксимации VPU побитно.
Embedding и residual — FP32. Поэтому **побитовое совпадение проверено для
INT8 MM на эталонных векторах; для полного LLM такого утверждения нет**.

## HBM и время

Численная модель хранит веса и cache в массивах MATLAB. Параллельно с каждым
действием выполняется учёт HBM-трафика на уровне тензоров (`llm_event`).
Полный 8-гигабайтный массив и AXI-сигналы не выделяются. Каждая порция
трафика округляется до 64 байт; предполагается равномерное распределение
по активным каналам. INT8 веса включают шкалу строки и смещения групп.

Предел одного направления порта — 32 байта/uclk. Конечное число слотов
ограничивает чтение как `64*RD*uclk/(read_latency+9)`, запись — аналогично
с WD и `write_latency+7`. На канал два порта; сверху вводится предел
native-стороны `64*core_clk` на канал. Для каждого тензора добавляется одна
задержка запуска; длительность операции равна `max(memory_s, compute_s)`:
идеальное потоковое перекрытие чтения весов и MXU. Последовательные операции
и слои друг с другом не перекрываются.

KV на слой и токен: запись `2*kv_heads*head_dim*4` байт, чтение — столько же,
умноженное на длину контекста. Прочитанные K/V повторно используются между
query heads внутри GQA-группы. Есть явный учёт RMSNorm scales; промежуточные
активации считаются находящимися во внутренней памяти. Ограничения размещения
TMEM/ACT, IMEM, очередей DMA и spills не моделируются.

Для M=1 MXU использует одну строку из MCOLS; оценка тактов одной проекции —
`ceil(N/S)*ceil(K/D)`. QACT и векторные функции оцениваются по LANES и числу
арифметических операций. Это допущение о производительности, а не исполнение
секвенсора/ISA или точная модель VPU latency. Значения циклов всего LLM нельзя
приравнивать к измерениям платы.

Частота ядра/архитектура берутся из TOML. uclk=225 MHz, read_latency=40,
write_latency=48 тактов — изменяемые **допущения**, не замеры HBM IP.
Результаты profile показывают тенденции и узкие места при этих допущениях;
полный профиль большой модели не выдаёт логиты/текст.

## Отдельная модель native/HBM

Для изучения адаптера сохранён более подробный независимый эксперимент:

```matlab
% cmd — массив struct: beat, write, data (64 uint8), mask (64 logical).
h = otpu.hbm(cmd,c);
[physical_byte_address,pc,port] = otpu.hbm_address(0:255,1,c);
```

`hbm_address` точно повторяет `otpu_hbm_amap`: CH_BASE, PC_GRAN, PC_XOR,
выбор native-порта битом 7 beat. `hbm` хранит затронутые beat в
`containers.Map`, начальное значение 0, и моделирует RAW/WAR/WAW, частичные
записи, конечные RD/WD, выдачу по порядку каждого порта и общий возврат
не более одного beat за такт. RD удерживается до возврата native-данных.
Есть issue/complete/return_cycle, dep_wait/slot_wait и итоговая память.

Это событийная модель, без точной структуры AQ/WQ, кольцевых ID, AXI
backpressure, RMW `otpu_mem_ch`, CDC и протокольных ошибок. Метрики ожиданий
не равны точным RTL st_dep. Эта модель не подключена к численному декодеру;
для большого LLM используется описанный выше агрегированный учёт тензоров.

## Проверки

`test_otpu` проверяет:

- 4 JSON-набора upstream: обычные данные, динамический диапазон/отброшенные
  группы, нулевые строки, halfway rounding и крайние экспоненты/FTZ.
  Сверяются коды, смещения, целые накопители и биты FP32 масштабов/результата;
- адресную перестановку и её обратимость на 8321 beat (включая конец канала),
  6 PC_GRAN × 2 PC_XOR × 4 канала;
- 700 случайных команд с масками против последовательной памяти,
  RD/WD=1/4/32, явные RAW/WAR/WAW, порядок и единственность возврата;
- численную генерацию, размерность/конечность логитов, рост KV,
  отсутствие влияния будущих позиций cache, независимость численного
  результата от частот, ограничения контекста и ёмкости;
- совпадение времён численного и символьного LLM при одинаковых размерах.

Фактический прогон — `verification.log` (не отслеживается Git). Эталонный
`fixtures/int8_mx.json` переносим: Python для обычного запуска не нужен.
В нём записаны SHA upstream и SHA256 `fp32.py`, `quant.py`, `isasim.py`.
Эталон вычислен `fp32.quantize_mx`, публичным `quantize_mxu` и формулами
`isasim::_mm`; полный интерпретатор ISA при генерации векторов не запускался.
Перегенерация из корня репозитория:

```bash
PYTHONPATH=../external/rtl/opentpu-fesens/patched \
../external/rtl/opentpu-fesens/.venv/bin/python \
    vcu128_otpu/sim/matlab/export_reference.py
```

RTL/Hog/upstream не меняются. Эти проверки дополняют существующие cocotb/
pytest, не заменяют их; новая FPGA-сборка и проверка на плате не выполнялись.

## Маршруты данных (исправлено 20.10.2026)

События трассы следуют путям upstream `otpu_slice` (подробно — `../../doc/inference.md`):
MM `q,k,v,o,gate,up,down,lm_head,attn_scores,attn_pv`: HBM → MXU (+ ACT RAM) → TMEM;
`*_qact`: TMEM → QUANT → ACT; `kv_write`: TMEM → QUANT → HBM (QST);
`attn_softmax` и прочие векторные: TMEM → VPU → TMEM; `embedding`: HBM → TMEM (LD);
`logits_store`: TMEM → HBM (ST). Прежняя версия отправляла attention на VPU и писала
KV как FP32 — это не соответствовало RTL.
