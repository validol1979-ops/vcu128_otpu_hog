# otpu_hbm_port — канал памяти openTPU на HBM2

`otpu_hbm_port.sv` подключает сторону контроллера upstream-модуля `otpu_mem_ch`
(`c_*`, два native-порта LiteDRAM, домен `uclk`) к двум AXI3-портам Xilinx HBM IP
(PG276). Один экземпляр — один канал памяти (2 GiB). Весь модуль работает в домене
`uclk` (план — 225 МГц); переходы между тактами остаются внутри `otpu_mem_ch`.
Контракт — `../../doc/design.md`, раздел «Контракт otpu_hbm_port».

В файле три модуля:

| Модуль | Назначение |
|---|---|
| `otpu_hbm_port` | адаптер канала |
| `otpu_hbm_amap` | отображение номера beat в адрес HBM (комбинационное) |
| `otpu_hbm_fifo` | синхронная FIFO, LUTRAM, выходы из регистров |

Тесты — `../../sim/hbm/` (`run.sh`), описание и результаты — ниже.

## Параметры

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `CH_BASE` | `33'h0` | байтовый адрес канала в глобальном пространстве HBM, кратен 2 GiB (канал `j` — `j × 2 GiB`) |
| `PC_GRAN` | 0 | log2 числа соседних beat, которые лежат подряд в одном псевдоканале (0…4, см. ниже) |
| `PC_XOR` | 1 | номер псевдоканала XOR со следующими тремя битами beat |
| `RD` | 32 | слоты чтения на порт: ARID, буфер данных чтения (2^k, 4…64) |
| `WD` | 32 | слоты записи на порт: AWID (2^k, 4…64) |
| `WQ` | 8 | FIFO данных записи на порт, beats |
| `AQ` | 4 | FIFO AR и AW на порт |

## Порты

Сторона `otpu_mem_ch` — те же имена и разрядности, что у его портов `c_*`
(направления обратные): `c_cmd_valid/ready/we/addr[1:0][24:0]`,
`c_wdata_valid/ready/data[1:0][511:0]/we[1:0][63:0]`,
`c_rdata_valid[1:0]`, `c_rdata_data[1:0][511:0]` (обе половины — одна шина).

AXI3 к HBM IP, по одному на порт `p` (упакованные массивы `[1:0]`, порт `p` →
`AXI_xx` HBM IP разводится на верхнем уровне):

| Сигнал | Разрядность | Значение |
|---|---|---|
| `m_aw*`, `m_ar*` | ADDR 33, ID 6, LEN 4, SIZE 3, BURST 2 | LEN = 1 (два слова), SIZE = 5 (32 байта), BURST = INCR |
| `m_wdata/wstrb/wlast` | 256 / 32 / 1 | WSTRB — из `c_wdata_we` (младшая половина beat — первое слово) |
| `m_wid` | 6 | WID AXI3 (= AWID); у HBM IP такого входа нет — не подключать |
| `m_wdata_parity` | 32 | XOR битов каждого байта WDATA (чётная чётность); нужен, только если в IP включена чётность данных записи — полярность сверить с PG276 |
| `m_b*` | ID 6, RESP 2 | BREADY = 1 |
| `m_r*` | ID 6, DATA 256, RESP 2, LAST | RREADY = 1; RDATA_PARITY не используется |

Состояние (для регистров платформы `otpu_hbm_regs`, домен `uclk`):

| Выход | Смысл |
|---|---|
| `st_rcmd[p]`, `st_wcmd[p]` (32) | команды чтения / записи, принятые от `otpu_mem_ch` |
| `st_rout[p]`, `st_wout[p]` (7) | операции в HBM сейчас: AR выдан и последний R не пришёл / AW выдан и B не пришёл |
| `st_dep[p]` (32) | такты, в которые голова порта ждала зависимость по beat |
| `st_busy[p]` | в порту есть команда, данные или операция |
| `st_err_cnt` (16) | ответы ≠ OKAY: каждое слово R с RRESP ≠ 0 и каждый B с BRESP ≠ 0, насыщается |
| `st_err` | был ответ ≠ OKAY (держится до `urst`) |
| `st_perr` | HBM нарушил протокол: R/B с ID без операции, RLAST не на втором слове (держится до `urst`) |

Сброс `urst` синхронный, активный 1, сбрасывает всё, включая счётчики.

## Отображение адресов

`b` — номер 64-байтного beat в канале (25 бит), `G = PC_GRAN`:

```
pc  = b[G+2:G] ^ (PC_XOR ? b[G+5:G+3] : 0)          // псевдоканал в канале, 3 бита
off = { b[24:G+3], b[G-1:0] }                         // 22 бита: beat внутри псевдоканала
адрес HBM = { CH_BASE[32:31], pc, off, 6'b0 }         // 33 бита
```

При глобальной адресации HBM (переключатель включён) адрес[32:28] — номер
псевдоканала (256 МБ), поэтому канал `j` занимает псевдоканалы `8j … 8j+7`,
а `pc` выбирает один из них.

Обоснование:

- **Взаимно однозначно.** `off` содержит все биты `b`, кроме `b[G+2:G]`, в том
  числе `b[G+5:G+3]`; по `off` и `pc` они восстанавливаются:
  `b[G+2:G] = pc ^ b[G+5:G+3]`. Окно канала — ровно 2 GiB от `CH_BASE`.
  Проверено перебором всех 2^25 beat (`tb_amap`).
- **Поток по соседним блокам идёт через разные псевдоканалы.** Блок — `2^G`
  соседних beat; любые 8 выровненных соседних блоков лежат в 8 разных
  псевдоканалах (XOR с константой внутри группы — перестановка). Тоже
  проверено перебором для каждого набора параметров теста.
- **XOR** разносит шаги, кратные 8 блокам (при простом `pc = b[G+2:G]` шаг в 8
  блоков бил бы в один псевдоканал): при шаге 8 блоков `pc` меняется вместе с
  `b[G+5:G+3]`. Шаг, кратный 64 блокам, по-прежнему остаётся в одном
  псевдоканале.
- **Внутри псевдоканала** адреса последовательны: beat блока и блоки, попавшие
  в один псевдоканал, идут подряд по `off`, что сохраняет попадания в открытую
  строку (раскладка строк/банков внутри псевдоканала — настройка HBM IP).
- **Порт.** `otpu_mem_ch` выбирает порт битом 7 номера beat, т. е. порт
  получает подряд 128 соседних beat. Биты псевдоканала `b[G+2:G]` лежат ниже
  бита 7 при `G ≤ 4`: тогда каждая серия из 128 beat одного порта проходит все 8
  псевдоканалов. При `G ≥ 5` серия одного порта занимает меньше псевдоканалов
  (при `G = 5` — 4), поэтому рекомендуются `PC_GRAN = 0…2`; по умолчанию 0
  (каждый следующий beat — следующий псевдоканал, 64 байта = 2 обращения BL4
  псевдоканала по 32 байта). Выбор на плате — по замеру.

## Механизм зависимостей

Каналы чтения и записи HBM (и разные ID внутри канала) между собой не
упорядочены, поэтому порядок по beat внутри порта держит адаптер. Одинаковые
beat всегда приходят на один порт (`otpu_mem_ch`: порт = бит 7), межпортовых
зависимостей нет.

- **Таблицы порта.** Слот чтения (`RD`, кольцо, ARID = слот): `r_pend` — чтение в
  HBM до последнего R, `r_beat` — его beat. Слот записи (`WD`, кольцо,
  AWID = слот): `w_v` — запись в HBM до B, `w_beat`. Слот записи занимается
  только свободный (если старейший ещё ждёт B, выдача записи ждёт).
- **Правило.** Новая команда ждёт каждую невыполненную запись того же beat (RAW,
  WAW); команда записи ещё и каждое невыполненное чтение того же beat (WAR).
  Чтение после чтения не ждёт. Запись «выполнена» по B, чтение — по последнему R
  (данные уже в буфере, дальнейшие записи их не меняют).
- **Конвейер.** Команда принимается в регистр A; в такте приёма её beat
  сравнивается со всеми записями таблиц (CAM, `RD + WD` компараторов по 25 бит)
  → вектор зависимостей `a_rdep/a_wdep` (бит на слот). Операция, которую голова H
  выдаёт в этом же такте (её ещё нет в таблице), добавляется отдельным
  компаратором `h_beat == beat`. Пока команда ждёт в A и H, биты гаснут по
  завершению операций (`r_fr`, `w_fr` — регистрованные onehot «R/B пришёл»); при
  переходе A→H снова добавляется операция, выдаваемая H в этом такте. Готовность
  головы `h_ok = вектор пуст` — регистр, вычисляется на такт вперёд. Поэтому на
  пути `c_cmd_ready` нет ни CAM, ни свёртки вектора; без коллизий порт выдаёт
  команду каждый такт.
- Выдача — строго в порядке команд порта (голова ждёт — ждут и следующие); это
  и даёт порядок по beat вместе с правилом выше.
- Освобождение консервативно: слот гаснет через 1–2 такта после B/R.

## Запись

`otpu_mem_ch` кладёт данные записи в FIFO порта в такте, когда команда входит в
очередь команд порта, поэтому данные записи уже на голове `c_wdata`, когда её
команда на `c_cmd`. Адаптер принимает команду записи только вместе с данными:
`c_cmd_ready` для записи требует `c_wdata_valid` и места в WQ,
`c_wdata_ready = c_cmd_valid & c_cmd_ready & c_cmd_we` (данные чтения команд
не трогают). Данные ждут в WQ; пакет W (2 слова, WLAST на втором) начинается
только после того, как HBM принял его AW (счётчик `w_cred`), поэтому W никогда
не опережает AW, а порядок W совпадает с порядком AW.

## Чтение

AR выдаётся, только если в кольце чтения порта есть свободный слот — место
для данных зарезервировано, поэтому RREADY = 1 и R принимаются в любом порядке
ID, в том числе с чередованием слов разных пакетов (слово 0 → `r_lo[ID]`,
слово 1 → `r_hi[ID]`, `r_half` по ID). Beat уходит в `otpu_mem_ch`, когда у
головы кольца пришли оба слова — в порядке команд порта, без обратного
давления. Арбитр двух портов выбирает не больше одного beat за такт (при
конфликте — по очереди), поэтому `c_rdata_valid` никогда не равен `2'b11`;
данные — регистр, обе половины `c_rdata_data` одинаковы.

Задержки по RTL: AR на шине через 3 такта после приёма команды (A, H, FIFO);
`c_rdata_valid` через 4 такта после последнего R.

## Тайминг (225 МГц, VU37P) и ресурсы

Не синтезировалось (Vivado в этой работе не запускался). Заложено: все выходы
AXI и `c_rdata_*` — из регистров; входы R и B регистрируются; CAM — отдельная
ступень (A) с регистром результата; `h_ok`, `rs_ok`, `ws_ok`, место в FIFO —
регистры, `c_cmd_ready` — 2–3 уровня LUT от регистров. Длинные разветвления:
`c_cmd_addr` на `RD + WD` компараторов, разрешения `m_wready` на 320 разрядов
W, мультиплексор шины чтения (1024 разряда) — Vivado тиражирует. Если входы
HBM (`*READY`) окажутся критичными, между адаптером и HBM IP ставится
регистровый срез AXI.

Ориентировочно на порт при `RD = WD = 32`: CAM — 1 600 триггеров и ~600 LUT
компараторов; буфер чтения — 32 × 512 бит LUTRAM; WQ — 8 × 576 бит LUTRAM.

## Пропускная способность

Предел одного порта — шина AXI 256 бит: 32 байта/такт `uclk` на чтение и
32 на запись (7,2 ГБ/с каждое при 225 МГц); канал (два порта) — 64 байта/такт
на чтение. Чтобы скрыть задержку HBM `L` тактов, порту нужно
`RD ≥ (L + ~8) / 2` слотов: при `RD = 32` — до `L ≈ 56`.

Фактические замеры — в разделе «Тесты».

Модель HBM (`hbm_model.py`, своя, AXI3): каждое чтение читает память в свой
случайный момент после AR, каждая запись пишет в свой после AW и обоих W —
задержки каналов чтения и записи независимы, так что чтение, выданное после
записи, часто выполняется раньше неё («обгоны» в таблице); R и B разных ID
возвращаются в произвольном порядке, слова R разных ID чередуются; случайное
обратное давление на AW/W/AR, паузы R/B, редкие полные остановки. Проверяются
порядок и данные чтения по эталону, итоговая память HBM против эталона, адреса

## Ограничения

- Синтез и тайминг в Vivado не проверены; на плате не запускалось.
- Предположения о HBM IP, которые проверяет только плата: после B запись видна
  последующим чтениям (любой ID); ответы одного ID — в порядке; полярность
  `WDATA_PARITY`. Адаптер не полагается на порядок ответов разных ID.
- Порт адаптера = один AXI-порт HBM: 32 байта/такт на направление. Порт
  выбирает `otpu_mem_ch` битом 7, поэтому последовательный поток идёт сериями по
  128 beat через один порт, и чтение потоком у связки ниже 64 байт/такт (замер
  ниже).
- Не больше 64 операций каждого вида на порт (ID 6 бит), т. е. задержка HBM
  скрывается до ~120 тактов только при `RD = 64`.
- Зависимости по beat сериализуют обращения к одному beat (в том числе WAW);
  пересылки данных записи в чтение нет.
- При глобальной адресации поток каждого порта идёт во все 8 псевдоканалов
  канала через переключатель HBM; цена боковых переходов переключателя — по
  замеру на плате (`PC_GRAN`).
- `urst` не ждёт операций в HBM: сбрасывать адаптер вместе с портами HBM
  (`AXI_xx_ARESET_N`) или после их опустошения (`st_busy = 0`), иначе поздние
  R/B после сброса дадут `st_perr`.
