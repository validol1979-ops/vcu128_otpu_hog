# VCU128 openTPU: устройство проекта

Перенос openTPU (FeSens, `external/rtl/opentpu-fesens`, коммит `f237dab`,
Apache-2.0) на VCU128 (xcvu37p-fsvh2892-2L-e). Ядро и оболочка upstream
(`rtl/top`, `mxu`, `vpu`, `mem`, `seq`, `dma`, `shell`, `tech/xilinxus`) не
меняются; заменяются только внешние стороны оболочки, как у цели BCU1525:

| BCU1525 (upstream) | VCU128 (этот проект) |
|---|---|
| LiteDRAM DDR4 на канал (native-порты) | `otpu_hbm_port`: native-порты → AXI HBM2 (Xilinx HBM IP) |
| XDMA Gen3 x16: DMA (AXI4) + BAR0 (AXI-Lite) | `eth40` + `otpu_eth_bridge`: 40G Ethernet (QSFP1) → те же AXI4 и AXI-Lite |
| хост: `XdmaTransport` | хост: `EthTransport` (тот же интерфейс транспорта) |

## Этапы

1. S = 1 (один слайс, 2 канала памяти), ядро 100 МГц: первые токены
   LFM2.5-230M, побитовое совпадение с симулятором ISA upstream.
2. S = 2…4, частота ядра 150–200 МГц, раскладка по SLR.

## Карта адресов (как у BCU1525)

DMA (данные): канал `j` (= 2s + c, слайс s, его канал c) — байтовые адреса
`j × 2 GiB` … `+2 GiB`. Регистры (BAR0 у XDMA):

| Адрес | Что |
|---|---|
| 0x00000 | `otpu_board` s_ctl (12 бит адреса; карта upstream `docs/observability.md`) |
| 0x30000 | SYSMON (температура, напряжения) — этап 2, до этого чтение 0 |
| 0x40000 | регистры HBM/платформы этого проекта (`otpu_hbm_regs`): калибровка, температура HBM, счётчики портов |
| 0x50000 | регистры 40G (`eth40_regs`): link, счётчики MAC/протокола, MAC/IP |

## Тактирование

| Такт | Источник | Частота | Домены |
|---|---|---|---|
| core_clk | default_100mhz_clk (BH51/BJ51) → MMCM | 100 МГц (этап 2: до 200) | `otpu_board`, native-сторона `otpu_mem_ch`, s_ctl |
| core_clk2x | тот же MMCM | 2 × core_clk | TMEM_PMP = 1 (если включено) |
| uclk | MMCM от 100 МГц HBM | 225 МГц | сторона контроллера `otpu_mem_ch`, `otpu_hbm_port`, AXI-порты HBM |
| hbm_ref | 100 МГц SiTime (HBM/DDR4 component clock) | 100 МГц | HBM_REF_CLK IP |
| apb | core_clk | 100 МГц | APB HBM (калибровка) |
| eth_clk | l_ethernet tx_clk_out (QSFP1, квад 135, Si570 156,25 МГц) | 156,25 МГц (40G, 256 бит) | `eth40`, `otpu_eth_bridge`, xclk-сторона `otpu_mem_ch` |
| dclk | core_clk | 100 МГц | DRP/init l_ethernet |

Переходы: native ↔ uclk ↔ xclk — внутри `otpu_mem_ch` (upstream);
AXI-Lite eth_clk → core_clk — асинхронный мост (verilog-axi `axil_cdc`).

## Контракт `otpu_hbm_port` (один канал памяти)

Подключается к стороне контроллера `otpu_mem_ch` (`c_*`, домен uclk) —
это контракт native-порта LiteDRAM, как его описывает заголовок
`otpu_mem_ch.sv`:

- два порта (p = 0, 1; upstream разводит команды по чётности банка, бит 7
  номера beat); на каждом: команда (`c_cmd_valid/ready/we/addr`, addr —
  номер 64-байтного beat в канале, 25 бит = 2 GiB), данные записи
  (`c_wdata_valid/ready/data/we`), в порядке команд записи порта;
- данные чтения: `c_rdata_valid[p]` в порядке команд чтения порта, **без
  обратного давления**, одна общая шина `c_rdata_data[0]`: два порта в одном
  такте — нарушение контракта (`n_err` в `otpu_mem_ch`);
- порядок по beat: команда порта, принятая после записи (или чтения) того же
  beat, видит её результат. AXI HBM не упорядочивает чтения и записи между
  собой — адаптер обязан сам держать зависимости RAW и WAR по beat;
- частичных записей `otpu_mem_ch` не выдаёт (делает RMW сам), но `c_wdata_we`
  передаётся в WSTRB.

Сторона HBM: на каждый порт свой AXI3-порт HBM IP (256 бит, uclk), beat =
пакет из двух 256-битных слов. Канал `j` занимает 2 GiB глобального
адресного пространства HBM (`j × 2 GiB`); при S = 4 — все 8 ГБ. Внутри
канала адреса перемешиваются по псевдоканалам (хеш) так, чтобы поток по
соседним beat шёл через разные псевдоканалы группы; точная функция —
в README адаптера.

## 40G: требования к протоколу

- Физика: `l_ethernet` 3.3, 40GBASE-R, 4 × 10,3125 Гбит/с, AXIS 256 бит,
  опорная 156,25 МГц — конфигурация из `rfsoc_8x8_40g_compat_hog`
  (проверена на ConnectX-3 до 27,5 Гбит/с), квад 135 (QSFP1). На ПК —
  ConnectX-3 `enp8s0`, отдельная подсеть, MTU 9000.
- UDP поверх IPv4, ответ на ARP (как `compat_arp_rx/tx` из RFSoC), кадры
  ARP/PAUSE и чужие — не ломают приём.
- Надёжность на стороне ПК: номер последовательности, подтверждения,
  повтор; повторно пришедшая запись не портит память (идемпотентна по
  адресу); операции регистров с побочным эффектом (старт программы) —
  защищены от повторного выполнения (кэш ответа по SEQ, как в 1G-мосте
  `vcu128_opentpu_hog`).
- Операции: запись памяти (до ~8 КиБ данных в кадре, адрес канала + смещение,
  целые 64-байтные beat), чтение памяти (запрос диапазона → поток ответных
  кадров), запись/чтение регистров (пачкой), опрос регистра на плате
  (`(reg & mask) == val` с таймаутом — заменяет циклы опроса хоста).
- Цель по скорости: запись в HBM ≥ 2 ГБ/с, чтение ≥ 2 ГБ/с с ПК на Python
  (крупные кадры, окно из многих пакетов в полёте).
