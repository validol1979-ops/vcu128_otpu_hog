# Часть 0. Проект в целом

Проект запускает языковые модели (LFM2.5-230M, Qwen3.5-2B/4B) на отладочной плате AMD
**VCU128** (Virtex UltraScale+ xcvu37p, **8 ГБ HBM2** в корпусе ПЛИС). Вычислительное ядро —
открытый ускоритель **openTPU** (FeSens, Apache-2.0), перенесённый с родной платы **BCU1525**.
Ядро и оболочка upstream не меняются; заменены только внешние стороны:

| BCU1525 (upstream) | VCU128 (этот проект) | Чей код |
|---|---|---|
| DDR4 через LiteDRAM | HBM2 через адаптер `otpu_hbm_port` | проект |
| PCIe XDMA (DMA + BAR0) | 40G Ethernet (UDP), мост `otpu_eth_bridge` | проект |
| `XdmaTransport` на ПК | `EthTransport` (`tools/otpu_eth.py`), тот же интерфейс | проект |

Суть одной фразой: **ПК компилирует модель в образ памяти и программу из инструкций
ускорителя, по 40G заливает их в HBM, на каждый токен пишет несколько регистров и командует
RUN; плата прогоняет все слои, ПК читает логиты и выбирает следующий токен.**

Структура репозитория:

```
vcu128_otpu_hog/
├─ Hog/              сабмодуль системы сборки (не патчить)
├─ Top/otpu/          проект Hog: hog.conf (чип), list/ (состав: .sv, IP, ограничения)
└─ vcu128_otpu/
   ├─ src/            RTL: otpu_vcu128_top.sv (верх), hbm/, eth40/, регистры платформы,
   │                  otpu-fesens/ (копия RTL upstream = upstream + патчи), lib/ (verilog-axi)
   ├─ ip/             hbm_0, eth40_qsfp1 (l_ethernet), jtag_axi_0
   ├─ constr/         пины, CDC, TMEM → URAM
   ├─ target/vcu128.toml   «паспорт» конфигурации ускорителя (общий для RTL и компилятора)
   ├─ tools/          ПК: транспорт, чат, бенчмарки, эмулятор платы
   ├─ sim/            hbm, eth40 (регрессии), lens, pysim, inference, matlab
   └─ doc/            документация
```

Сборка: `./Hog/Do CREATE otpu`, затем `./Hog/Do WORKFLOW -njobs 4 otpu` (результат в `bin/`).

# Часть I. Языковая модель как математический объект

## I.1. Текст → токены

**Токен** — элементарная единица текста для модели: не буква и не слово, а кусок слова
(«пре», «образ», «ование», пробел+буква…). Текст режется на токены **токенизатором**, обычно
**BPE (byte-pair encoding)**: на большом корпусе алгоритм итеративно склеивает самые частые
пары байт в новые символы — получается словарь частых подстрок.

**Словарь (vocabulary, vocab)** — конечный список всех токенов модели, пронумерованных
0…V−1; у LFM2.5-230M V = 65 536. Для модели текст — последовательность целых
`t₀, t₁, …, t_{P−1}` из {0…V−1}.

**Специальные токены** — служебные номера: начало/конец реплики, **EOS (end of sequence)** —
«текст закончен».

**Чат-шаблон** — правило, по которому диалог («система: …, пользователь: …, ассистент: …»)
оборачивается в специальные токены перед подачей модели.

## I.2. Что модель вычисляет: распределение следующего токена

Языковая модель — функция

```
f(t₀, …, t_{n−1}) → z ∈ ℝ^V
```

Вектор **z** — **логиты (logits)**. Логит zᵢ — ненормированный логарифм вероятности того,
что следующий токен — i:

```
P(t_n = i | t₀…t_{n−1}) = softmax(z)ᵢ = e^{zᵢ} / Σⱼ e^{zⱼ}
```

то есть `zᵢ = log P(i) + C` с общей для всех i константой C. Название — из статистики
(logit(p) = log(p/(1−p)), логарифм шансов); в многоклассовом случае так называют вход softmax.

**Softmax** переводит произвольный вещественный вектор в распределение: всё положительно,
сумма 1, порядок сохраняется. Инвариантен к сдвигу всех zᵢ на константу — поэтому перед
экспонентой вычитают max(z) (численная устойчивость).

## I.3. Генерация: авторегрессия и сэмплирование

**Авторегрессия** — генерация по одному токену: вычислили z, выбрали tₙ, дописали ко входу,
повторили. DSP-аналогия — БИХ-структура, где выход подаётся на вход.

**Сэмплирование (sampling)** — правило выбора tₙ по z:

- **greedy (жадный)** — tₙ = argmax z (детерминированно);
- **температура T** — softmax(z/T): T < 1 обостряет распределение, T > 1 сглаживает;
- **top-k** — оставить k самых вероятных, перенормировать, выбрать случайно;
- **top-p (nucleus)** — оставить минимальный набор лучших с суммарной вероятностью ≥ p.

**Детокенизация** — обратное преобразование номеров в текст.

## I.4. Внутренности: трансформер

Модель — композиция однотипных **слоёв** (layers, блоков декодера). Между ними передаётся
**скрытое состояние (hidden state)** — вектор xₙ ∈ ℝ^H для каждой позиции n; H — **скрытая
размерность** (LFM2.5: 1024). **Позиция (pos)** — порядковый номер токена в
последовательности: 0, 1, 2, …

**Эмбеддинг (embedding).** Вход первого слоя: `x = E[tₙ]`, E ∈ ℝ^{V×H} — **таблица
эмбеддингов**: номер токена просто выбирает строку. Эмбеддинг — обученный «вектор смысла»
токена.

**Веса (weights, параметры)** — все матрицы и векторы модели, полученные обучением
(E, матрицы проекций, γ норм…). При работе модели (**инференсе**, inference) постоянны.
«230M», «2B» в названиях — число параметров (230 млн, 2 млрд).

**Активации** — всё, что вычисляется из входа во время работы (x, q, k, v, промежуточные
векторы); меняются от токена к токену.

### Один слой (декодер в стиле LLaMA/Qwen)

```
h  = x + Attention(RMSNorm(x))        ← смешивание по времени (между позициями)
x' = h + MLP(RMSNorm(h))              ← нелинейность по каждой позиции отдельно
```

**Residual (остаточная связь)** — сложение `x + F(x)`: подблок вычисляет поправку к x, а не
новый x (иначе глубокую сеть не обучить). DSP-аналогия: прямая ветвь плюс параллельный фильтр.

### RMSNorm

```
RMSNorm(x) = x / sqrt(mean(x²) + ε) ⊙ γ
```

Вектор делится на своё среднеквадратичное значение (нормировка по мощности) и поэлементно
(⊙, произведение Адамара) умножается на обученный γ ∈ ℝ^H; ε — защита от деления на 0.
DSP-аналогия: АРУ по RMS на каждой позиции.

### Attention (механизм внимания)

Единственное место, где позиции «смотрят» друг на друга.

1. **Проекции:** `q = W_q·x`, `k = W_k·x`, `v = W_v·x` — query (запрос), key (ключ), value
   (значение): три линейных отображения одного вектора.
2. **Головы (heads):** q, k, v режутся на n_h кусков размерности d (**head dim**, 64…128);
   каждая голова — независимый «канал» внимания.
3. Для текущей позиции n и каждой головы:
   ```
   sᵢ = (q · kᵢ) / √d          для всех прошлых позиций i ≤ n   ← скоры (scores)
   pᵢ = softmax(s)ᵢ                                            ← веса внимания
   o  = Σᵢ pᵢ · vᵢ                                             ← выход
   ```
   q сравнивается скалярным произведением со всеми прошлыми ключами, получается
   распределение «на кого смотреть», ими взвешиваются значения. Деление на √d держит
   дисперсию скоров около 1. DSP-аналогия: адаптивный КИХ-фильтр, коэффициенты (pᵢ) которого
   зависят от данных и пересчитываются на каждый выходной отсчёт.
4. **Причинность (causal mask):** смотреть можно только на i ≤ n. В матричной форме — добавка
   −∞ к запрещённым скорам (**аддитивная маска**).
5. **O-проекция:** выходы голов склеиваются и умножаются на W_o.

**GQA (grouped-query attention):** голов q больше, чем голов k/v; например, 16 голов q делят
2 **KV-головы** — каждая KV-голова обслуживает **группу** голов q. Экономит память KV.

**q/k-norm** — дополнительная RMSNorm над q и k внутри головы (Qwen3).

### RoPE (rotary position embedding)

Attention сам по себе не знает порядка (сумма инвариантна к перестановке). Позиция вносится
поворотом: компоненты q и k разбиваются на пары, каждая пара — комплексное число, умножается на
`e^{j·pos·θ_m}`, θ_m = base^{−2m/d} — набор «частот»:

```
q̃ = q · e^{j·n·θ},  k̃ᵢ = kᵢ · e^{j·i·θ}   ⇒   Re(q̃ · conj(k̃ᵢ)) зависит только от (n − i)
```

DSP-аналогия: модуляция набором несущих — скалярное произведение двух модулированных сигналов
зависит только от разности фаз, т. е. от относительного сдвига. Поэтому нужны таблицы cos/sin
по позиции и поэтому в программу передаётся позиция.

### MLP (FFN, feed-forward network) с GLU

```
g = W_gate·x,  u = W_up·x            (ℝ^H → ℝ^F, F ≈ 3–4·H — промежуточная размерность)
h = SiLU(g) ⊙ u                      ← GLU (gated linear unit): одна ветка «открывает» другую
y = W_down·h                         (ℝ^F → ℝ^H)
SiLU(g) = g · σ(g),   σ(g) = 1/(1+e^{−g})   (логистическая сигмоида)
```

Поэлементная нелинейность между двумя линейными отображениями, на каждой позиции отдельно.
Здесь основная масса весов модели.

### LM head (языковая «голова»)

После последнего слоя `z = W_head · RMSNorm(x)`, W_head ∈ ℝ^{V×H} — это и есть логиты.
У LFM2.5 это 65 536 × 1024 = 64 МиБ в INT8.

### Не-attention слои моделей проекта

- **LFM2 short-conv:** в части слоёв (у LFM2.5-230M — 8 из 14) вместо attention короткая
  **свёртка по времени** с 3 отводами и гейтами: `b = B⊙x'`,
  `y = (Σ_{k<3} c_k ⊙ b_{n−k}) ⊙ C`. Буквально КИХ 3-го порядка по оси позиций, отдельный на
  каждый из H каналов, с модуляцией на входе и выходе. Нужна **линия задержки** прошлых b —
  кольцевой буфер в памяти (отсюда аргумент `ring`).
- **Qwen3.5 Gated DeltaNet:** рекуррентный слой с матричным состоянием S ∈ ℝ^{d×d} на голову:
  `Sₙ = αₙ·Sₙ₋₁·(I − βₙ kₙkₙᵀ) + βₙ vₙkₙᵀ`, выход `oₙ = Sₙ qₙ`. По сути **LMS/NLMS-обновление**
  (дельта-правило) с забыванием αₙ: каждая голова — адаптивный фильтр, который по ходу текста
  учится отображать k → v. Состояние лежит в HBM, обновляется командами `DSTEP/STREAM`.

## I.5. Prefill, decode и KV-кэш

**KV-кэш.** Ключи kᵢ и значения vᵢ прошлых позиций не меняются (зависят только от прошлого
входа), поэтому их **хранят** — на каждый слой и каждую KV-голову. Новый токен считает только
свои q, k, v, дописывает k, v в кэш и читает кэш целиком для attention. DSP-аналогия: линия
задержки КИХ-фильтра, только растущая.

**Контекст** — все токены, которые модель «помнит» (длина KV-кэша); **cap** — максимальная
длина, на которую выделена память.

**Prefill** — обработка промпта: все P токенов известны, их гонят пачками по R строк
(матрица·матрица). **Decode (декод)** — генерация по одному токену (M = 1 строка): каждый слой —
**умножение матрицы весов на вектор**, каждый вес используется ровно один раз на токен.

## I.6. Почему декод упирается в память

На каждый вес INT8 (1 байт) — 2 операции (умножение + сложение): **арифметическая
интенсивность** 2 оп/байт. Чтобы получить токен, надо **прочитать все веса модели** (LFM2.5 —
около 220 МиБ с LM head). Значит

```
время токена ≥ (байт весов на токен) / (пропускная способность памяти)
```

Режим, где предел — память, а не умножители, называется **memory-bound** (обратный —
**compute-bound**). Отсюда вся архитектура ускорителя: веса **потоком** текут из памяти прямо
в умножители; отсюда и выигрыш от 4-битных весов — вдвое меньше байт, вдвое быстрее.

## I.7. Квантование: блочная плавающая точка

**Квантование весов** — хранение не в FP32, а в INT8 или 4-битных форматах (int4, **fp4** —
4-битная плавающая точка, **nvfp4** — её вариант с блочными множителями). Это та же **блочная
плавающая точка (BFP)**, что в БПФ-процессорах:

```
W[n, k] ≈ w[n,k] · 2^(−dw[n, блок]) · Sw[n]
          int8      степень 2 на блок    FP32-масштаб на строку
                    из 32 элементов
```

Активации перед умножением квантуются так же (`Sa`, `da`). Произведения INT8 суммируются
**точно в целом**, блочные сдвиги — точные степени двойки, FP32 появляется один раз в конце.
Поэтому результат не зависит от порядка суммирования и **совпадает бит в бит** с эталонным
симулятором — на этом построена вся проверка проекта.

**FP32** — 32-битная плавающая точка IEEE-754; **i2f** — перевод целого в FP32.

# Часть II. Чем вычисляется: ПЛИС, память, шины, сеть

## II.1. ПЛИС (FPGA) и её ресурсы

**ПЛИС (FPGA)** — микросхема, логика которой задаётся конфигурацией (какие ячейки как
соединены). Схема описывается на HDL — здесь **SystemVerilog** (`.sv`). Ресурсы xcvu37p:

| Ресурс | Что это |
|---|---|
| **LUT** (look-up table) | 6-входовая таблица истинности: любая логическая функция 6 переменных |
| **FF** (flip-flop, триггер) | 1 бит памяти, обновляется по фронту такта |
| **DSP48E2** | аппаратный умножитель 27×18 с 48-битным сумматором-аккумулятором — та самая MAC-ячейка |
| **BRAM** | блочная память 36 Кбит, двухпортовая |
| **URAM** (UltraRAM) | крупный блок 288 Кбит; в проекте в нём TMEM |
| **SLR** (super logic region) | xcvu37p собран из 3 кристаллов-«этажей»; переход между ними (**SLL**) дорог по задержке; HBM подключена только к нижнему SLR0 |
| **GTY** | высокоскоростной последовательный приёмопередатчик (SerDes), до ~30 Гбит/с на линию |

**Битстрим (bitstream)** — файл конфигурации ПЛИС. Путь: **синтез** (HDL → сеть LUT/FF/DSP),
**имплементация** (размещение и трассировка), генерация битстрима — всё в **Vivado** (САПР
AMD/Xilinx). **Hog** — надстройка: собирает проект Vivado из списков файлов в git и вшивает в
прошивку версию (SHA коммита; `GLOBAL_SHA` → регистр `BUILD_ID`).

**IP-ядро (IP)** — готовый блок производителя, сконфигурированный файлом `.xci`; здесь три:
контроллер HBM, 40G Ethernet (`l_ethernet`), JTAG-to-AXI.

## II.2. Такт, домены, конвейер

**Такт (clock)** — периодический сигнал, по фронту которого все триггеры одновременно
запоминают входы. Синхронная схема = регистры + комбинационная логика между ними.
DSP-аналогия: система с дискретным временем, такт — отсчёт.

**Тайминг:** сигнал должен пройти логику между регистрами за период. **Slack** — запас;
**WNS** (worst negative slack) — худший запас по setup (< 0 — частота недостижима), **WHS** —
по hold. «Тайминг закрыт» — WNS ≥ 0 и WHS ≥ 0.

**MMCM** — синтезатор частот на ПЛИС (ФАПЧ): из 100 МГц делает VCO 900 МГц и делит его.
**BUFG** — глобальный буфер тактовой сети. Такты проекта:

| Такт | Источник | Частота | Кто на нём |
|---|---|---|---|
| `core_clk` | QDR4_CLK_100MHZ → MMCM, 900/6 | 150 МГц | ядро openTPU, шина регистров |
| `uclk` | тот же MMCM, 900/4 | 225 МГц | AXI-порты HBM, `otpu_hbm_port` |
| `clk100` | тот же MMCM, 900/9 | 100 МГц | APB HBM, DRP трансиверов |
| `hbm_ref` | DDR4_CLK_100MHZ | 100 МГц | опорный HBM IP |
| `eth_clk` | `tx_clk_out` l_ethernet | 312,5 МГц (3,2 нс по `clocks.rpt`, журнал) | весь 40G-мост |

(В [design.md](design.md) у `eth_clk` указано 156,25 МГц — это частота опорного Si570, а не
выходного такта; в ранних записях журнала — «322 МГц», позже уточнено до 312,5.)

**Тактовый домен** — набор триггеров на одном такте. **CDC (clock domain crossing)** —
передача данных между доменами с несоизмеримыми частотами. Прямое подключение даёт
**метастабильность** (триггер, вход которого меняется в момент фронта, может «зависнуть» между
0 и 1), поэтому — синхронизаторы из 2–4 триггеров для одиночных бит и **асинхронные FIFO** или
рукопожатия для данных. Ограничения на них — `constr/vcu128_cdc.tcl`.

**Сброс (reset)** — сигнал приведения схемы в начальное состояние; «держать блок в сбросе» —
он стоит.

**Конвейер (pipeline)** — разбиение вычисления на стадии с регистрами между ними: результат
через несколько тактов (**латентность**), но новый вход каждый такт (**пропускная
способность**).

**FIFO** — очередь «первым пришёл — первым ушёл», буфер между производителем и потребителем.

**Рукопожатие valid/ready:** источник выставляет данные и `valid = 1`, приёмник — `ready = 1`;
передача происходит в такте, где оба 1. **Обратное давление (back-pressure)** — приёмник держит
`ready = 0`, источник ждёт.

## II.3. Память

**DRAM** — динамическая память: большая, но медленная и неравномерная. Данные в **банках** и
**строках**; открыть строку дорого, читать подряд из открытой — дёшево, поэтому DRAM отдаёт
**пачками (burst)**. **Латентность** — время от запроса до данных (~100+ нс); **пропускная
способность** — байт/с в установившемся потоке. Для полного потока нужно держать много
запросов **в полёте** (in flight).

**HBM2 (High Bandwidth Memory)** — DRAM в виде стопки кристаллов в одном корпусе с ПЛИС,
соединённой очень широкой шиной. На VCU128 — два стека по 4 ГБ; каждый — 8 каналов × 2
**псевдоканала (PC)**, всего 32 псевдоканала по 256 МБ, работающих **независимо и
параллельно**. Для полной скорости поток разбрасывают по псевдоканалам: адреса
**хэшируются**, чтобы соседние куски попадали в разные PC.

**Калибровка** — процедура после включения: контроллер подстраивает задержки линий под
конкретную микросхему; до её конца память использовать нельзя (биты `STATUS.CALIB0/1`).

**Контроллер памяти** — схема, превращающая «прочитай адрес A» в команды DRAM. **LiteDRAM** —
открытый контроллер, под который написан upstream openTPU; его интерфейс — **native-порт**
(команда, данные, ответы строго по порядку).

**TMEM, IMEM, ACT RAM** — память на кристалле (BRAM/URAM): маленькая (сотни КиБ), доступ за
такт без задержек.

## II.4. Шины AXI

**AXI4** — стандартная шина ARM/Xilinx для доступа к памяти, 5 независимых каналов с
valid/ready: **AW** (адрес записи), **W** (данные записи), **B** (ответ «запись выполнена»),
**AR** (адрес чтения), **R** (данные чтения). Транзакция может быть **пачкой** (AxLEN + 1 слов
подряд). У транзакций есть **ID**; ответы разных ID могут приходить **не по порядку** — HBM IP
этим пользуется. **AXI3** — предыдущая версия (у HBM IP порты AXI3). **WSTRB** — маска байт
записи. **RRESP/BRESP** — код ответа (OKAY, SLVERR, DECERR).

**AXI-Lite** — упрощённая AXI для регистров: без пачек, одно 32-битное слово за транзакцию.
**AXI-Stream (AXIS)** — поток без адресов: `tdata`, `tvalid`, `tready`, `tlast` (конец
пакета), `tkeep` (действительные байты), `tuser` (служебный бит; у MAC — «кадр битый»).

**Мастер / ведомый (master / slave):** мастер инициирует транзакции, ведомый отвечает.
**Коммутатор (xbar, crossbar)** соединяет нескольких мастеров с несколькими ведомыми по адресу.

**Регистр управления (CSR)** — ячейка адресного пространства, запись/чтение которой управляет
схемой или читает её состояние. **Карта регистров** — таблица адресов и их смысла. Карта
проекта: 0x00000 — `otpu_board` (ядро), 0x40000 — регистры платформы/HBM, 0x50000 —
`eth40_regs`, 0x60000 — регистры `l_ethernet`.

**DMA (direct memory access)** — блок, который сам копирует массивы между памятями.

## II.5. Сеть

**Ethernet-кадр** — пакет канального уровня: MAC назначения и источника (по 6 байт),
**EtherType** (что внутри; 0x0800 — IPv4), полезная нагрузка, **FCS** (CRC-32 для обнаружения
ошибок).

**MAC-адрес** — аппаратный адрес интерфейса; **MAC (как блок)** — схема, формирующая и
разбирающая кадры. **PCS/PMA** — физический уровень (кодирование 64b/66b, выравнивание линий).
**40GBASE-R4** — 40 Гбит/с как 4 линии по 10,3125 Гбит/с. **QSFP** — разъём-модуль на 4
линии; **DAC** — пассивный медный кабель между модулями.

**IPv4** — сетевой уровень (IP-адреса, заголовок с контрольной суммой). **UDP** — транспорт
поверх IP: порты, без гарантий доставки, порядка и повторов. **ARP** — «у кого IP X? — у меня,
мой MAC такой-то»; без него ПК не знает, куда слать кадр. **PAUSE** — служебный кадр «притормози».

**MTU** — максимальный размер полезной нагрузки кадра: стандартный 1500, **jumbo-кадры** —
9000 (8 КиБ данных в кадре).

Надёжность поверх UDP сделана в протоколе проекта ([eth40_protocol.md](eth40_protocol.md)):

- **SEQ** — номер запроса; **подтверждение (ack)** — ответ платы; **повтор по таймауту**;
- **окно** — сколько запросов отправлено без ожидания ответов (здесь 12): скрывает задержку
  сети;
- **идемпотентность** — повтор не меняет результат: запись тех же байт туда же — да;
  «запусти программу» — нет, поэтому есть **кэш ответа**: повтор с тем же SEQ получает
  сохранённый ответ, операция не повторяется;
- **sendmmsg / recvmmsg** — вызовы Linux «много UDP-пакетов за один вызов», нужны для
  гигабайтных скоростей (`tools/otpu_eth_fast.c`).

**JTAG** — отладочный интерфейс микросхемы через USB-кабель; **JTAG-to-AXI** — IP, через
который можно читать и писать регистры без сети.

# Часть III. Ускоритель openTPU

## III.1. Ускоритель, ISA, компилятор

**Ускоритель** — специализированный вычислитель под узкий класс задач (здесь инференс LLM),
управляемый **программой**.

**ISA (instruction set architecture)** — набор команд: какие инструкции есть, как кодируются,
что делают. Здесь инструкция — 8 слов по 32 бита (32 байта): **опкод** (что делать), **поля
адресов** (где операнды), **флаги** (модификаторы).

**Компилятор** (Python на ПК, upstream `opentpu`, см. [compiler.md](compiler.md)) превращает
модель в образ памяти и программы. В ПЛИС компилятора нет.

**ISA-симулятор** — программа на ПК, исполняющая инструкции бит-точно, но без тактов. Эталон:
логиты платы должны совпасть с ним **бит в бит** (`validate.py --against isa`).

**Конфигурация** ускорителя — `target/vcu128.toml` (S = 1, D = 128, MCOLS = 4, TMEM 65536 слов,
IMEM 32768 слов = 4096 инструкций, 150 МГц…). Из неё считается **ARCH_HASH**, зашитый в RTL;
ПК сверяет его с регистром `CFG_HASH` — иначе программы были бы скомпилированы под другое
железо.

## III.2. Слайс и его блоки

**Слайс** — одно полное вычислительное ядро (сейчас S = 1). При S > 1 веса делятся по строкам
между слайсами, каждый читает свою часть — поток растёт в S раз.

| Блок | Что делает |
|---|---|
| **SEQ (секвенсор)** | устройство управления: читает инструкции, ведёт регистры R0..R15 и аппаратные циклы, раздаёт работу |
| **IMEM** | память программы на кристалле, 4096 инструкций |
| **DMA** | HBM ↔ TMEM (`LD` — load, `ST` — store) |
| **MXU** (matrix unit) | матрица × вектор/матрица: 4 колонки × 128 умножителей INT8 на DSP48E2 (`MM`) |
| **ACT RAM** | INT8-копии активаций — неподвижные операнды MXU, ≤ 4 строки |
| **QUANT** | квантователь FP32 → INT8: в ACT RAM (`QACT`) или прямо в HBM (`QST`, запись KV-кэша) |
| **VPU** (vector unit) | 8 полос FP32: поэлементные операции, exp2, 1/x, 1/√x, суммы, максимумы (`VOP`) |
| **TMEM** | 256 КиБ FP32, рабочая память активаций, 8 банков |
| **COLL** | обмен между слайсами (при S = 1 почти не используется) |

**Порты памяти слайса:** **B** — 128 байт/такт, главный (DMA, поток весов в MXU, загрузка
программы); **A** — 32 байта, масштабы весов; **SW** — 32-битные слова для QST.

**Банки TMEM:** 8 независимых частей (адрес mod 8); за такт в банк пишется одно слово. Кто
пишет — решает **арбитр** по приоритету DMA > COLL > VPU > выгрузка MXU > QUANT; разрешение —
**грант**.

**Стационарный операнд:** в MXU активации (M ≤ 4 строки) лежат неподвижно в ACT RAM, а веса
**текут** мимо потоком — это соответствует memory-bound задаче: каждый вес прочитан один раз и
сразу использован.

**Чанк** — 128 байт = 128 весов INT8, единица потока в MXU; строка весов длины K — KB = K/128
чанков. **Beat** — 64 байта, единица обмена с контроллером памяти; чанк = 2 beat.

## III.3. Как секвенсор исполняет программу

- **pc (program counter)** — номер текущей инструкции.
- **Регистры R0..R15** — 32-битные целые внутри SEQ. К адресным полям инструкции перед раздачей
  прибавляются регистры (`w1 += R[ra]`), поэтому адрес **аффинный**: база + регистр.
- **LI / ADDI** — загрузить константу в регистр / прибавить к нему.
- **LOOP** — аппаратный цикл (до 4 уровней вложенности).
- **Окно (window)** на 16 мест: SEQ не ждёт окончания инструкции — кладёт её в окно и идёт
  дальше.
- **Отпечаток (footprint)** — какие диапазоны TMEM, HBM, ACT RAM инструкция читает и пишет.
- **Конфликты (hazards):** **RAW** (read-after-write — младшая читает то, что старшая ещё не
  записала), **WAR** (write-after-read — младшая пишет туда, откуда старшая ещё читает),
  **WAW** (write-after-write — обе пишут в одно место).
- **Табло (scoreboard)** — таблица этих конфликтов; блок берёт инструкцию, только когда все её
  конфликтующие старшие завершены.
- **Dispatch → issue → retire** — положить в окно → начать исполнение на блоке → завершить и
  освободить место. **ICOUNT** — счётчик завершённых инструкций.

Итог: инструкции **перекрываются** во времени, но результат тот же, что при строго
последовательном исполнении (**последовательная семантика**).

## III.4. Команды

| Команда | Смысл |
|---|---|
| `LD` / `ST` | HBM → TMEM / TMEM → HBM через DMA |
| `MM` | `out[j,n] = Σk ACT[j,k] · W[n,k]`: веса из HBM, активации из ACT RAM, результат FP32 в TMEM |
| `QACT` | TMEM (FP32) → INT8 в ACT RAM со своим масштабом Sa |
| `QST` | TMEM → INT8 → HBM (дописать k, v в KV-кэш) |
| `VOP` | операция VPU: `ADD MUL MAX EXP2 RECIP RSQRT RSSQ` (Σx²) `RMAX ARGMAX` … |
| `DSTEP` / `STREAM` | шаг DeltaNet над состоянием в HBM |
| `LI`, `ADDI`, `LOOP` | регистры и циклы (исполняются в SEQ) |
| `HALT` | конец программы (`HALT CHAIN` — загрузить следующую и продолжить) |
| `RLD` | значение из TMEM → регистр SEQ (генерация на плате) |

**Флаги MM:** **ACC** — прибавить к старому значению в TMEM; **ASCALE** — `старое·α + новое`;
**RMAX** — заодно максимум строки; **RSC** — масштаб на строку из отдельного массива (K-кэш);
**UNIT** — без масштаба весов.

**Эпилог MM** — последняя стадия, перевод целой суммы в FP32:
`y = i2f(acc) · Sw[n] · Sa[j] · 2^−16`, затем ACC/ASCALE/RMAX.

# Часть IV. Жизненный цикл одного токена

**Пример:** чат с LFM2.5, промпт обработан, KV-кэш содержит 300 позиций. Генерируем **токен
на позиции `pos = 300`**; вход — токен `tok`, выбранный на прошлом шаге.

## Фаза 0. Что уже сделано (один раз за сеанс)

1. **Подключение.** ПК открывает UDP-сокеты к 192.168.41.2:20308, читает `ID`, `CAPS`
   (битовая маска возможностей прошивки: ARGS, GEN, CHASH, …) и `CFG_*` (конфигурация),
   сверяет `CFG_HASH` и калибровку HBM.
2. **Компиляция образа.** Из **чекпойнта** Hugging Face (файлы весов обученной модели;
   Hugging Face — общий репозиторий моделей) строится **образ**: квантованные веса всех слоёв,
   LM head, таблицы эмбеддингов и RoPE, место под KV-кэш, **I/O-область** для логитов. Слои
   лежат **блоками одинакового размера** — тогда один `LOOP` обходит все, сдвигая адрес.
3. **Загрузка образа** в HBM по сети: около 8 с, 2,2–2,7 ГБ/с.
4. **Раскладка по каналам.** Слайс видит одно линейное пространство, физически оно чередуется
   по двум каналам HBM по 64 байта: beat `b` → канал `b mod 2`, с **CHASH** (XOR-перестановка
   по чётности). Хост раскладывает данные так же (`board.py`: `beat_at`, `split`).
5. **Prefill:** промпт токенизирован с чат-шаблоном и прогнан пачками по ≤ 4 строки; KV-кэш
   позиций 0…299 заполнен.

## Фаза 1. ПК готовит прогон (`Engine.step(tok)`, `qwen3.py:2603`)

**1.1. Выбор программы.** Attention обрабатывает KV-кэш **блоками по 256 позиций**
(`ATTN_BLOCK = 256`), число блоков зашито в программу. Поэтому позиции разбиты на **корзины
(buckets)** по 256; позиция 300 — корзина 2 (256…511). Одна программа обслуживает все позиции
корзины — **резидентный декод** («программа живёт в IMEM»). Позиция и токен приходят
**аргументами** (`RunPos.values`):

```
tpos = pos mod 256 = 44      ← позиция внутри корзины
tok  = номер входного токена
ring = (pos+1) mod 3          ← указатель линии задержки свёрток LFM2
```

Программы корзин компилируются **заранее в фоне** (`_prefetch`: за `DECODE_LEAD = 16` позиций
до границы) и кэшируются на диске (**progcache**).

**1.2. Аргументы → 8 слов.** Компилятор знает, какие адреса программы зависят от tok, tpos,
ring (например, `адрес строки эмбеддинга = база_E + tok · байт_в_строке`). `arg_words` вычисляет
8 машинных слов **ARG0..7**, которые станут регистрами R8..R15.

**1.3. Подготовка области логитов.** I/O-область заранее заливается **sentinel** — значением,
которое программа не запишет (`0xFFFFFFFF`, NaN в FP32). Нет sentinel в последнем beat куска —
кусок готов: так ПК читает логиты **во время прогона**, без флагов готовности. (Вариант
`fill_logits`: программа сама заливает область значением `0xFF800000`.)

## Фаза 2. Запись регистров ARG: путь одного слова от Python до триггера

`Board.set_args` пишет только **изменившиеся** ARG (обычно tok и tpos).

1. **ПК, `EthTransport.reg_batch`.** UDP-пакет протокола: заголовок 22 байта
   (`MAGIC "OT40"`, SEQ, OP = 3 «REG», CH, OFFSET, LEN = число операций, AUX) и операции по
   16 байт (`1<<28 | адрес`, значение). Уходит через ConnectX-3 `enp8s0`, MTU 9000.
2. **Физика.** QSFP1 → 4 GTY-линии (квад 135) → IP `l_ethernet` (PCS + MAC) проверяет FCS и
   выдаёт кадр как AXIS, 32 байта за такт `eth_clk`, бит ошибки — `tuser`.
3. **Фильтр** (`eth40_rx_filter`): свой MAC, IPv4 без опций и фрагментов, UDP, свой IP и порт,
   контрольная сумма IP-заголовка, MAGIC. Чужие, ARP (идут в ответчик `eth40_arp_rx`) и PAUSE —
   выбрасываются целиком.
4. **Кадровая FIFO** (128 КиБ) отдаёт кадр дальше только целиком и только без ошибок.
5. **Диспетчер** (`eth40_disp`) по OP направляет кадр в автомат REG (`eth40_regx`): тот
   проверяет **все** операции пачки, затем выполняет по одной как транзакции AXI-Lite; ключ
   `(SEQ, IP, порт)` и ответ кладёт в **кэш ответа**.
6. **CDC.** Адрес 0x00060 не в окне 0x5xxxx (регистры самого моста), поэтому транзакция идёт
   через `axil_cdc` из `eth_clk` в `core_clk`.
7. **Коммутатор** `vcu128_axil_xbar` (мастера — сеть и JTAG; ведомые — ядро, платформа,
   l_ethernet) по адресу ведёт запись в `otpu_ctrl`: `arg[k] <= wdata` (`otpu_ctrl.sv:247`).
8. **Обратно:** ответ B → плата формирует кадр «OT4R» с тем же SEQ (`eth40_ctl_tx` →
   `eth40_tx_mux` → l_ethernet TX) → ПК получает подтверждение. Круг — десятки микросекунд.

## Фаза 3. Загрузка программы (только при смене корзины)

`Board.load_program` (`board.py:1032`):

1. Слова программы пишутся в HBM **WRITE-кадрами** по 8 КиБ: `eth40_wr` → пачки AXI4 → тракт
   памяти (фаза 5.5) → HBM. Подтверждение кадра — **после B** (данные в памяти). Окно 12
   кадров; повтор безопасен (идемпотентно).
2. Регистры: `CTRL = 0`, `PROG_ADDR`, `PROG_N` (число инструкций), `CTRL = LOAD`.
3. `poll(STATUS.LOADING == 0)` — **опрос на плате**: одна REG-операция «читай регистр, пока
   `(reg & mask) ≠ val` или не истёк таймаут» вместо сотен сетевых чтений.
4. **Загрузчик** слайса ждёт отсутствия чтений в полёте и читает программу из HBM через порт B
   в IMEM по 4 инструкции (128 байт) за такт.

Корзина та же — программа уже в IMEM, фазы нет (`BoardBackend.start`: `_resident`).

## Фаза 4. Пуск

`Board.start` (`board.py:1135`): `CTRL = CLEAR` (обнулить счётчики), `CTRL = RUN`, чтение
`STATUS` — убедиться, что бит RUN поднялся (RUN не принимается без калибровки HBM).

В железе (`otpu_ctrl`): RUN **отпускает слайс из сброса**, **R8..R15 ← ARG0..7**, `pc = 0`,
счётчик **CYCLES** начинает считать такты `core_clk`.

## Фаза 5. Внутри слайса (~1,9 млн тактов для LFM2.5)

### 5.1. Программа токена

```
ВХОД
  LD  E[tok]        адрес = база + R[ARG от tok]     → TMEM: x ∈ ℝ^1024 (FP32)
  LD  cos, sin       адрес = таблица + R[ARG от tpos]

LOOP по 14 слоям (адрес блока слоя += размер блока в конце итерации):

  RMSNorm:
    VOP RSSQ, MUL 1/H, ADD ε, RSQRT        → скаляр r = 1/√(mean(x²)+ε)     (VPU)
    QACT RSCALE+CSCALE                      → ACT RAM ← int8(x · r · γ)      (QUANT)

  если слой attention:
    MM ×(2+групп)       k = W_k·x̂, v = W_v·x̂, q = W_q·x̂                    (MXU)
    VOP                 q/k-norm, RoPE-поворот пар (cos/sin)                (VPU)
    QST ×2              K[pos] ← int8(k), Vᵀ[:, pos] ← int8(v) в HBM         (QUANT)
    для каждой KV-головы, для каждого блока b из 256 прошлых позиций:
      QACT              ACT ← int8(q · log₂e / √d)
      MM RSC+RMAX       s = q · K[b]ᵀ      — блок K-кэша течёт из HBM «как веса»
      VOP MAX, EXP2SUB  m' = max(m, max s);  p = 2^(s − m');  α = 2^(m − m')
      QACT              ACT ← int8(p)
      MM UNIT+ACC+ASCALE  acc = α·acc + p · Vᵀ[b]
      VOP               l = α·l + Σp;  m = m'
    VOP RECIP, MUL      o = acc / l
    QACT, MM, VOP ADD   x += W_o · o                                  (residual)

  если слой short-conv (LFM2):
    MM                  [B, C, x'] = W_in · x̂
    VOP MUL, ST         b = B ⊙ x' → кольцо задержки в HBM (позиция ring)
    VOP MUL/ADD         y = (Σ_{k<3} c_k ⊙ b_{n−k}) ⊙ C               (КИХ по времени)
    QACT, MM, VOP ADD   x += W_out · y

  MLP:
    RMSNorm → QACT
    для каждого куска f промежуточной размерности F:
      MM, MM            g = W_gate[f]·x̂,  u = W_up[f]·x̂
      VOP ×5            h = g · σ(g) · u        (σ из EXP2, ADD, RECIP)
      QACT, MM +ACC     y += W_down[:, f] · h
    VOP ADD             x += y

  ADDI, LOOP

ФИНАЛ
  RMSNorm → QACT
  MM ×8 по 8192 строк   z[c] = W_head[c] · x̂        (кусками: FP32-результат куска
                                                    должен поместиться в TMEM)
  ST                    куски логитов → I/O-область HBM
HALT
```

Пояснения:

- **x̂** — INT8-копия нормированного x в ACT RAM.
- **Разделение RMSNorm:** VPU считает только скаляр r, умножение `x·r·γ` QUANT делает
  «бесплатно» при квантовании (флаги RSCALE/CSCALE).
- **Онлайн-softmax («flash attention»):** softmax по прошлым позициям считается блоками по 256
  без хранения всех скоров: ведутся текущий максимум m, знаменатель l и числитель acc; при
  росте максимума старое домножается на α = 2^(m−m'). То же, что перенормировка блочной
  плавающей точки при росте экспоненты блока. Используется `exp2`: `e^x = 2^(x·log₂e)`, поэтому
  q заранее умножен на log₂e/√d.
- **Vᵀ** — V хранится транспонированным, тайлами по 256 позиций: тогда `p · Vᵀ` для MXU —
  обычная «матрица весов × вектор».
- **KV-кэш в INT8** с FP32-масштабом на позицию; при чтении идёт через MXU как веса (масштабы K —
  через порт A, флаг RSC).
- Пока VPU и QUANT досчитывают блок b, MXU уже стримит q·Kᵀ следующих блоков.

### 5.2. Как секвенсор ведёт инструкции

Каждый такт:

1. **Выборка:** `ir ← IMEM[pc]`.
2. **Подстановка регистров:** `w1 += R[ra]`, `w2 += R[rb]`, `w3 += R[rc]`. Так R8..R15 (ARG)
   становятся адресами строки эмбеддинга, строки RoPE, места в KV-кэше, а адресные регистры,
   сдвигаемые `ADDI`, — адресами весов текущего слоя.
3. `LI`, `ADDI`, `LOOP` исполняются в SEQ.
4. Остальные — в **окно**: отпечаток, отметка RAW/WAR/WAW со старшими; выборка сразу дальше.
5. Свободный блок берёт самую старую свою готовую инструкцию (**issue**); DMA, QUANT, COLL — по
   порядку, VPU может обогнать независимую младшую.
6. Закончив, блок сообщает `udone`: слот свободен, ICOUNT растёт (**retire**).

Поэтому веса следующей MM уже текут, пока VPU досчитывает RMSNorm, а QUANT квантует x.

### 5.3. Как MXU исполняет одну MM

1. **ustart (ACCEPT).** Как только у инструкции сняты конфликты по HBM, **issuer** MXU
   запрашивает чанки весов через порт B в **FIFO чанков** (1024 × 128 байт), масштабы — через
   порт A. Активации к этому моменту могут быть не готовы — это **предвыборка (prefetch)**.
   MXU держит две команды: пока одна досчитывается, веса следующей уже стримятся.
2. **urel (RELEASE).** Сняты все конфликты (QACT записал x̂ в ACT RAM) — умножение разрешено.
3. **Счёт строки n:** начинается, когда все KB чанков строки в FIFO; иначе MXU **голодает
   (starved)** — счётчик `MXU_STARVE`. За такт колонка j перемножает 128 пар INT8 на DSP48E2 и
   складывает **точно в целом**; блоки по 32 элемента выравниваются точными сдвигами
   `2^−(dw+da)`.
4. **Эпилог:** `y = i2f(acc) · Sw[n] · Sa[j] · 2⁻¹⁶`, затем ACC/ASCALE/RMAX.
5. **Выгрузка (drain):** до 2 FP32 за такт в TMEM при гранте на банки; отказ — счётчик
   `TMEM_DENY`.

При декоде M = 1: из 4 колонок работает одна. Предел — не умножители, а порт B:
**128 байт/такт × 150 МГц = 19,2 ГБ/с**. MXU занят ~99,9 % времени, VPU ~6,5 %, QUANT ~3 %
(Lens, LFM2.5, pos 8).

### 5.4. Запись K/V и логитов

- `QST`: QUANT квантует k и v в INT8 и через порт SW пишет 32-битными словами с маской байт;
  чтобы вписать байты в 64-байтный beat, `otpu_mem_ch` выполняет **RMW (read-modify-write)**:
  прочитать beat, заменить байты, записать.
- `ST` логитов: DMA из TMEM в I/O-область HBM, кусок за куском по ходу LM head.

### 5.5. Путь одного чанка весов от HBM до MXU (здесь код проекта)

```
issuer MXU: «128 байт по адресу A»                (core_clk, 150 МГц)
 │
 ▼ otpu_native_dram (upstream): 128 B = 2 beat по 64 B; beat b → канал (b mod 2), с CHASH
 ▼ otpu_mem_ch (upstream), на канал: CDC core_clk → uclk (225 МГц), арбитраж «ядро vs сеть»,
 │   команда native-порта LiteDRAM (we, номер beat 25 бит); порт p — бит 7 номера beat
 ▼ otpu_hbm_port (ПРОЕКТ), на канал:
 │   1) адрес: pc = b[2:0] ⊕ b[5:3] → один из 8 псевдоканалов канала;
 │      адрес HBM = {канал, pc, смещение, 6 нулей} — взаимно однозначно (перебор, tb_amap)
 │   2) подпорт: старший бит pc → один из NS = 2 AXI-портов (своего мини-коммутатора HBM)
 │   3) порядок: CAM сравнивает beat со всеми невыполненными операциями подпорта
 │      (RAW/WAR/WAW по beat) — AXI HBM не упорядочивает чтения и записи, upstream на порядок
 │      рассчитывает
 │   4) AR с ARID = номер слота буфера ответа, зарезервированного заранее
 ▼ HBM IP: AXI3-пачка из 2 слов по 256 бит (AxLEN = 1, AxSIZE = 5) → мини-коммутатор →
 │   псевдоканал → DRAM
 │
 ▲ R в ЛЮБОМ порядке ID → в свой слот; otpu_hbm_port отдаёт beat'ы строго в порядке команд,
 │   без обратного давления (поэтому слот резервируется ДО выдачи AR)
 ▲ otpu_mem_ch: CDC uclk → core_clk;  otpu_native_dram: 2 beat → 128 B
 ▲ FIFO чанков MXU
```

- **CAM (content-addressable memory)** — сравнение ключа со всеми записями таблицы
  параллельно, за такт.
- **Мини-коммутатор HBM** — группа из 4 AXI-портов IP с «ближними» псевдоканалами; доступ в
  чужую группу медленнее, поэтому каждый порт адресует только свои. Канал 0 — порты
  00 01 04 05, канал 1 — 08 09 12 13 (подробно — `src/hbm/README.md`).
- Native-порт принимает 64 байта за такт `uclk`, AXI-порт — 32, поэтому на каждый native-порт
  два AXI-порта (NS = 2), четыре на канал.

### 5.6. Конец прогона

SEQ встречает `HALT`, перестаёт выбирать и ждёт **пустого окна** → **STATUS.HALTED = 1**,
CYCLES стоп. **WR_IDLE** — отдельный бит «все записи приняты памятью»: HALTED значит лишь
«последний ST ушёл из ядра».

## Фаза 6. ПК во время прогона и после

**6.1. Перекрытие (пока плата считает).**

- Фоновый поток компилирует следующую корзину (если граница близко).
- Чат печатает предыдущий токен (`on_start`).
- **Стриминг логитов** (`_stream_logits`): ПК помнит, когда каждый кусок LM head был готов на
  прошлом токене, и за `STREAM_EARLY = 0,3 мс` до того читает последний beat куска. Sentinel
  нет — читает кусок целиком **READ-запросами** (плата отвечает потоком кадров по 8 КиБ,
  потерянное ПК перезапрашивает), проверяет, что sentinel нигде не осталось (beat'ы могут лечь
  не по порядку), и сразу отдаёт кусок сэмплеру.

**6.2. Ожидание конца** (`Board.wait`, `board.py:1168`):

1. `poll(STATUS.HALTED)` — опрос на плате; ожидаемое время прогона выучено по прошлым токенам.
2. Дождаться `WR_IDLE` — иначе чтение логитов могло бы обогнать их запись.
3. Одной пачкой прочитать счётчики: CYCLES, ICOUNT, B_RD (beat'ов прочитано портом B), B_WR,
   A_RD, SW_WR, B_STALL (такты ожидания порта B).
4. `CTRL = 0` — слайс снова в сбросе.
5. Проверить ERROR (недопустимая инструкция, таймаут WAITW) и AXI_ERR (тракт памяти) —
   исключение.

**6.3. Выбор токена.**

- Дочитать последний кусок логитов (`_stream_tail`), снова залить область sentinel (в фоне).
- **Сэмплирование:** argmax или softmax(z/T) с top-k/top-p и случайным выбором.
- Детокенизация, печать. EOS или лимит — стоп.
- `pos = 301`, `tok = выбранный` → фаза 1.

## Фаза 7. Альтернатива: весь цикл на плате (`generate_card`)

При бите **GEN** в CAPS: ПК один раз пишет блок состояния (токен, позиция, сколько
генерировать, параметры выборки, стоп-токены) и запускает программу. После LM head программа
сама делает `VOP ARGMAX` (или top-k), пишет номер в `out[]` в HBM, через `RLD` переносит его в
регистр SEQ — он становится адресом строки эмбеддинга — и `LOOP` повторяет токен. На границе
корзины **HALT CHAIN** подгружает следующую программу из HBM, сохраняя TMEM, HBM и R8..R15.
ПК только читает `out[]`: все сетевые круги фаз 1–4 и 6 исчезают.
