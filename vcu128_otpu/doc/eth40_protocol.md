# 40G Ethernet: протокол и мост «UDP ↔ AXI4 + AXI-Lite»

Замена XDMA upstream openTPU (BCU1525: DMA AXI4 в каналы памяти + BAR0 AXI-Lite к
регистрам) на 40G Ethernet VCU128: QSFP1 — DAC — Mellanox ConnectX-3 `enp8s0` на ПК.
Плата: `src/eth40/otpu_eth_bridge.sv` (+ `eth40_regs.sv`), ПК:
`tools/otpu_eth.py` (`EthTransport`, интерфейс `XdmaTransport`), эмулятор платы
`tools/otpu_eth_emu.py`. Тесты: `sim/eth40/run.sh` (RTL), `tools/test_otpu_eth.py` (ПК).

## 1. Тракт

```
l_ethernet RX (256 бит, без tready, tuser на TLAST = плохой кадр)
 ├─ eth40_arp_rx ───────────── запрос ARP на свой IP ─────────────┐
 └─ eth40_rx_filter ─ axis_fifo (кадровая, RXB = 128 КиБ, отбрасывает плохие и
       │               не наши кадры целиком, при переполнении — кадр целиком)
       └─ eth40_disp ─┬─ WRITE: eth40_wr  ─ AW/W (128 бит) → канал j; B → подтверждение
                      ├─ READ:  eth40_rd  ─ AR/R → кадры данных → FIFO данных (32 КиБ) ─┐
                      ├─ REG:   eth40_regx ─ AXI-Lite (20 бит) ; ответ + кэш ответа    │
                      └─ ошибка формата → ответ ST_BAD                                 │
 eth40_ctl_tx (подтверждения, ответы REG и ошибки) → FIFO служебных (8 КиБ) ─┐         │
l_ethernet TX ◄─ eth40_tx_mux (ARP, затем служебные, затем данные; по кадрам) ◄┴─────────┘
```

Всё в домене `eth_clk` (`tx_clk_out` l_ethernet, 156,25 МГц), сброс синхронный, активный 1.
Переход AXI-Lite в домен ядра и декодирование окон делает верхний уровень.

## 2. Кадр

Ethernet II + IPv4 (IHL 5, без опций) + UDP, затем заголовок протокола 22 байта: всего
64 байта, так что данные начинаются ровно с третьего 256-битного beat AXIS (байт n
кадра — `tdata[8*(n%32) +: 8]` beat n/32). Порт платы — параметр/регистр, по умолчанию
**20308 (0x4F54)**. Поля Ethernet/IP/UDP — сетевой порядок; поля протокола —
**little-endian**.

| Байт UDP | Поле | Запрос | Ответ |
|---|---|---|---|
| 0–3 | MAGIC | `0x3034544F` («OT40») | `0x5234544F` («OT4R») |
| 4–7 | SEQ | номер запроса | SEQ запроса |
| 8 | OP | 1 WRITE, 2 READ, 3 REG | OP запроса |
| 9 | CH / STATUS | канал памяти j = 2s + c | STATUS (ниже) |
| 10–13 | OFFSET | смещение в канале, байт | см. операции |
| 14–17 | LEN | см. операции | см. операции |
| 18–21 | AUX | READ: байт данных в ответном кадре (0 = 8192) | см. операции |
| 22… | данные | WRITE: LEN байт; REG: операции | READ: данные; REG: результаты |

STATUS: 0 OK, 1 ошибка AXI (SLVERR/DECERR), 2 неверный запрос (ничего не выполнено),
3 таймаут опроса.

Ответ уходит на MAC, IP и порт источника запроса (MAC — из кадра запроса, своего
ARP-кэша нет), с IP/порта платы; IPv4: ID 0, DF, TTL 64; контрольная сумма UDP 0
(кадр защищён FCS). Ответ без данных — 64 байта (не короче минимального кадра).

### WRITE (1) — запись памяти

Запрос: CH, OFFSET (кратно 64), LEN (кратно 64, 64…8192), LEN байт данных; OFFSET + LEN ≤
2 ГиБ, CH < NC, длина UDP = 30 + LEN. Иначе — ответ ST_BAD, память не трогается.
Данные пишутся пачками AXI INCR по 16 байт (до 256 beat, не через границу 4 КиБ),
WSTRB = все единицы (частичных beat нет — нет read-modify-write в `otpu_mem_ch`).
**Подтверждение** (OP 1, OFFSET/LEN запроса, AUX = канал) уходит только после B всех
пачек запроса: `otpu_mem_ch` даёт B, когда контроллер принял все beat пачки, поэтому
данные видны любому следующему доступу. Подтверждения — по порядку приёма запросов.
Повтор запроса безопасен (запись идемпотентна), на каждый — своё подтверждение.

### READ (2) — чтение памяти

Запрос: CH, OFFSET, LEN (кратно 64, OFFSET + LEN ≤ 2 ГиБ; длина не ограничена, ПК берёт
96 КиБ), AUX — размер кадра ответа (кратно 64, 64…8192; 0 = 8192). Ответ — поток из
⌈LEN/AUX⌉ кадров: SEQ запроса, OFFSET — смещение данных этого кадра в канале, LEN — их
длина, AUX — OFFSET запроса. Потерянные кадры ПК запрашивает заново (новый запрос на
недостающий кусок); кадры прежних запросов того же вызова тоже принимаются.

### REG (3) — пачка операций с регистрами

Запрос: LEN — число операций (1…256), за заголовком — операции по 16 байт:

| Слово | Запись (1) | Чтение (2) | Опрос (3) |
|---|---|---|---|
| 0 | `1<<28 \| addr` | `2<<28 \| addr` | `3<<28 \| addr` |
| 1 | данные | — | маска |
| 2 | — | — | значение |
| 3 | — | — | таймаут, такты eth_clk |

`addr` — байтовый адрес 20 бит, кратен 4; биты 27:20 — 0. Все операции проверяются
до выполнения: неверная — ответ ST_BAD, AUX = номер первой неверной, ничего не выполнено.
Выполнение — по одной транзакции AXI-Lite (WSTRB = 0xF). Опрос читает регистр подряд,
пока `(reg & mask) != value` и с начала операции не прошло `таймаут` тактов.
Ответ: OFFSET — число успешно выполненных операций, LEN — число слов результата, AUX —
RESP AXI неудачной операции; результаты — по слову на чтение и опрос (опрос — последнее
прочитанное значение), включая неудачную операцию. Остановка на первой ошибке: ST_AXI
или ST_TIMEOUT.

**Кэш ответа.** Плата хранит ключ (SEQ, IP, порт источника) и ответ последней
выполненной пачки. Запрос с тем же ключом не выполняется, а получает сохранённый ответ
(повтор ПК после потери ответа не запускает программу второй раз). Пока пачка
выполняется или её ответ отправляется, любой другой REG-запрос (и повтор того же)
молча отбрасывается (счётчик `req_busy`): ПК повторит по таймауту. Пачки выполняются
параллельно с записью и чтением памяти (свой автомат), поэтому долгий опрос не
останавливает DMA.

Запись IP или порта платы в `eth40_regs` действует сразу: ответ на такой запрос уже
уходит с нового адреса.

## 3. Что плата отбрасывает молча

Фильтр приёма (`eth40_rx_filter`) пропускает в разбор только кадр, у которого: MAC без
ошибки (tuser = 0 на TLAST), MAC назначения свой, EtherType 0x0800, IPv4 0x45, без
фрагментации (MF = 0, смещение 0), UDP, IP назначения свой, верная контрольная сумма
заголовка IPv4, свой порт UDP, длина UDP = длина IP − 20, кадр не короче 14 + длина IP
(хвост — выравнивание или FCS — допустим), полезная нагрузка ≥ 22 байт и начинается с
MAGIC запроса. Всё остальное — ARP (идёт в ответчик), PAUSE и другие кадры
управления MAC (0x8808, только счётчик), IPv6, чужие MAC/IP/порт, широковещательный UDP —
отбрасывается целиком и не влияет на следующие кадры. Переполнение FIFO приёма
отбрасывает кадр целиком (счётчик `rx_overflow`), ПК повторит.

ARP: ответ на запрос (oper 1, широковещательный или на свой MAC) о своём IP — по образцу
`compat_arp_rx/tx` из `rfsoc_8x8_40g_compat_hog`. Запрос, пришедший во время отправки
ответа ARP, теряется (ПК повторит).

## 4. Регистры `eth40_regs` (окно 0x50000)

AXI-Lite slave в домене eth_clk, адрес 8 бит внутри окна. Неизвестный адрес — 0, OKAY.

| Смещение | Имя | Доступ | Описание |
|---|---|---|---|
| 0x00 | ID | R | `0x30345445` («ET40») |
| 0x04 | VERSION | R | 1 |
| 0x08 | LINK | R | вход `link_stat` (состояние l_ethernet, синхронизирует верхний уровень; предлагается [0] stat_rx_status, [1] stat_rx_aligned, [7:4] block_lock по линиям) |
| 0x0C | STATUS | R | [0] запись в работе, [1] чтение в работе, [2] пачка REG в работе, [3] кэш ответа REG заполнен, [31:16] заполнение FIFO приёма (beat по 32 байта) |
| 0x10 | CTRL | W | [0] = 1 — сбросить счётчики |
| 0x14 | MAC_LO | R/W | MAC платы [31:0] (по умолчанию 02:00:5e:41:00:01 → `0x5E410001`) |
| 0x18 | MAC_HI | R/W | [15:0] — MAC [47:32] (`0x0200`) |
| 0x1C | IP | R/W | IP платы (`0xC0A82902` = 192.168.41.2) |
| 0x20 | PORT | R/W | [15:0] порт UDP (20308) |
| 0x24 | PARAMS | R | параметр `PARAMS` верхнего уровня (предлагается NC) |
| 0x40 + 4k | счётчик k | R | 32 бита, с переполнением |

Счётчики k: 0 `rx_frames` (все кадры MAC), 1 `rx_bad` (tuser MAC), 2 `rx_accept`
(запросы, принятые фильтром), 3 `rx_ignore` (исправные, но не наши: ARP, PAUSE, чужие),
4 `rx_overflow`, 5 `arp_req`, 6 `arp_tx`, 7 `mac_ctl` (0x8808), 8 `req_write`,
9 `req_read`, 10 `req_reg` (выполненные пачки), 11 `req_dup` (ответ из кэша),
12 `req_busy` (REG отброшен: пачка в работе), 13 `req_bad` (ответ ST_BAD), 14 `tx_frames`,
15 `rd_frames` (кадры данных чтения), 16 `axi_err` (ошибки B/R DMA или AXI-Lite).
`EthTransport.eth_info()` читает их все.

## 5. Интерфейс `otpu_eth_bridge`

Параметры: `NC` (каналов, 1…4; на плате 2 или 4), `RXB` (байт FIFO приёма, 131072),
`TXDB` (FIFO кадров чтения, 32768), `TXCB` (FIFO служебных, 8192), `MAXW` (8192),
`AQ` (записей в ожидании B, 32), `REGMAX` (256), `NEV` (17).

| Группа | Порты |
|---|---|
| такт | `clk` (eth_clk), `rst` (синхронный, 1) |
| адрес платы | `local_mac[47:0]`, `local_ip[31:0]`, `local_port[15:0]` — от `eth40_regs` |
| MAC RX | `rx_tdata[255:0]`, `rx_tkeep[31:0]`, `rx_tvalid`, `rx_tlast`, `rx_tuser` |
| MAC TX | `tx_tdata[255:0]`, `tx_tkeep[31:0]`, `tx_tvalid`, `tx_tlast`, `tx_tuser` (= 0), `tx_tready` |
| DMA (j < NC) | `x_awvalid/awready[NC]`, `x_awaddr[NC][30:0]`, `x_awlen[NC][7:0]`, `x_wvalid/wready/wlast[NC]`, `x_wdata[NC][127:0]`, `x_wstrb[NC][15:0]`, `x_bvalid/bready[NC]`, `x_bresp[NC][1:0]`, `x_arvalid/arready[NC]`, `x_araddr[NC][30:0]`, `x_arlen[NC][7:0]`, `x_rvalid/rready/rlast[NC]`, `x_rdata[NC][127:0]`, `x_rresp[NC][1:0]` |
| регистры | `m_axil_aw*/w*/b*/ar*/r*`, адрес 20 бит, данные 32 |
| в `eth40_regs` | `ev[NEV-1:0]` (импульсы событий), `status[31:0]` |

DMA — ровно порты `x_*` upstream `otpu_bcu_sys` (сторона XDMA `otpu_mem_ch`): адрес —
смещение в канале (бит 31 канала отброшен), INCR, AxSIZE 4 (16 байт; `awsize/awburst` не
выводятся — `otpu_mem_ch` их не принимает), без ID, ответы по порядку. AW выдаются
независимо от W и опережают данные. Мастер AXI-Lite держит не больше одной транзакции и
не меняет адрес до её конца — внешний декодер окон может быть комбинационным
(как `sim/eth40/tb_eth40.sv`).

Настройки l_ethernet (как в RFSoC-проекте, `CONFIGURATION_TX_REG1 = (12<<10)|(1<<1)|1`):
вставка FCS на TX включена (без неё ПК видит каждый кадр как bad FCS), удаление FCS на RX
(`ctl_rx_delete_fcs`, если выключено — 4 байта хвоста фильтр допускает),
`ctl_rx_max_packet_len` ≥ 8260 (кадр 64 + 8192 + FCS), `tx_tuser` = 0, RX без `tready`.

## 6. ПК: `EthTransport`

```python
import sys; sys.path.insert(0, "vcu128_otpu/tools")
from otpu_eth import EthTransport
from opentpu.host.board import Board
b = Board(transport=EthTransport("192.168.41.2"))
```

На ПК: `enp8s0` с адресом 192.168.41.1/24, MTU 9000 (кадр 64 + 8192 байт). root не нужен.

- Два подключённых UDP-сокета (память и регистры), у каждого свой SEQ и своя
  блокировка: опрос регистра из основного потока не ждёт передачи памяти из рабочего
  потока Board. Подключённый сокет держит одну очередь передачи ядра: кадры одного
  сокета не обгоняют друг друга (повтор записи не может прийти после следующей записи).
- `mem_write`: кадры по 8 КиБ, окно `window` = 12 кадров (~99 КиБ < 128 КиБ FIFO
  приёма); повтор кадра без подтверждения через `rto` (20 мс) с тем же SEQ, до `retries`
  (50). Диапазон не по границам 64 байт расширяется, крайние beat читаются и сливаются
  (как `XdmaTransport.mem_write`).
- `mem_read`: запросы по `read_req` (96 КиБ), не больше `read_window` (2) в полёте —
  в полёте не больше буфера приёма сокета (`net.core.rmem_max` по умолчанию 208 КиБ,
  ядро удваивает). Запрос без новых кадров дольше `rto` — недостающие куски
  запрашиваются заново.
- `reg_read/reg_write/reg_read_many/reg_write_many/reg_batch`: пачки до 256 операций,
  повтор с тем же SEQ (кэш платы — ровно одно выполнение); ошибки — `EthError`.
- `poll(off, mask, val, timeout, expect)`: опрос на плате отрезками `poll_slice`
  (10 мс) — между ними проверка общего таймаута (`TimeoutError`, как у XDMA) и Ctrl-C;
  `poll_exact = True`.
- Атрибуты для Board: `threaded`, `streams` = True, `ecc` = False (HBM без
  инициализации ECC с ПК, `Board.scrub` не нужен), `run_h2c` = 0 (нет ограничения XDMA
  H2C), `host_idle` = 0, `bases`, `devname` (`otpu-eth-<IP>`: замок устройства Board).
- Окна записи и чтения выполняет помощник на C (`otpu_eth_fast.c`: sendmmsg/recvmmsg,
  данные записи — из буфера пользователя, ctypes отпускает GIL); собирается `gcc` в
  `~/.cache/otpu_eth/` при первом использовании. Без gcc (или `OTPU_ETH_NOFAST=1`) —
  тот же алгоритм на Python.
- Для чтения быстрее 2 ГБ/с с запасом: `sudo sysctl -w net.core.rmem_max=67108864
  net.core.wmem_max=67108864` (однократно) и `read_window` 4–8.

## 7. Скорость и узкие места

| Звено | Предел |
|---|---|
| 40GBASE-R | 5 ГБ/с (256 бит × 156,25 МГц) |
| AXI DMA моста | 16 байт/такт = **2,5 ГБ/с на канал** (128 бит × 156,25 МГц) |
| `otpu_mem_ch` X-сторона | uclk 225 МГц × 64 байта = 14,4 ГБ/с, делится с ускорителем (RUN = 32, XT/XB: записи хоста пачками при работе ядра) |
| Запрос ПК | один `mem_write`/`mem_read` — один канал; Board пишет каналы слайса по очереди, поэтому скорость на канал = скорость `Board.write/read` |
| ПК (C, 127.0.0.1 против заглушки на C в том же ПК) | запись 0,96–2,04 ГБ/с, чтение 1,03–1,95 ГБ/с в 4 прогонах (оба конца делят loopback и CPU, ПК был загружен другими задачами); на реальной карте заглушки нет — оценка снизу |
| ПК (Python без C) | запись 0,4, чтение 0,6 ГБ/с против эмулятора на Python (его предел; путь C против того же эмулятора — 0,64/0,77) |

Измерено в RTL-симуляции (`sim/eth40` `test_throughput`, 256 КиБ в канал 0, без
пауз AXI и TX, окно ПК 12 кадров, 2026-10-19): **запись 15,64 байт/такт (2,44 ГБ/с),
чтение 15,59 байт/такт (2,44 ГБ/с)** при NC = 2 и NC = 4; с паузами AXI (~45 % тактов)
и TX — 8,35 байт/такт (ограничивает модель памяти). Накладные: 64 байта заголовка на
8 КиБ, 5 тактов подготовки заголовка кадра чтения, задержка подтверждения (окно 12 кадров
её покрывает). На плате добавятся задержка `otpu_mem_ch`/HBM и время ПК (ConnectX-3
в RFSoC-проекте проверена до 27,5 Гбит/с ≈ 3,4 ГБ/с — выше цели).

## 8. Ограничения

- Один канал на запрос; 2 ГБ/с — на канал, обе стороны (ПК, плата) не распараллеливают
  каналы внутри одного вызова `mem_write/mem_read`.
- Ошибка RRESP в чтении (otpu_mem_ch всегда OKAY) не портит кадр и не меняет STATUS —
  только счётчик `axi_err`; ошибка BRESP отмечает ST_AXI у подтверждения, забирающего
  эти B (точно — с точностью до запроса того же канала).
- Кэш ответа REG — одна запись: ПК держит не больше одной пачки в полёте на сокет;
  повтор старой пачки после новой будет выполнен снова (на прямом кабеле и
  подключённом сокете порядок сохраняется).
- Пока пачка REG выполняется (опрос), другие REG-запросы отбрасываются — ПК ждёт по
  таймауту; `poll_slice` ограничивает это время.
- IP-фрагментация и опции IPv4 не поддерживаются; UDP checksum не проверяется и не
  считается.
- Нет обратного давления MAC RX: при переполнении FIFO приёма теряется кадр целиком.
- Повтор ARP-запроса во время отправки ответа ARP теряется.
- `ctl_rx_max_packet_len`, FCS и прочие настройки l_ethernet — на верхнем уровне
  (без процессора, `eth40_mgmt`/регистры IP).

## 9. Проверки

RTL: `sim/eth40/run.sh` — cocotb 2.0.1 + Verilator 5.050, DUT `tb_eth40` (мост +
`eth40_regs`, AxiRam со случайными паузами всех каналов AXI, AxiLiteRam, кадры scapy,
TX с обратным давлением), по 10 тестов при NC = 2 и NC = 4: ARP; запись/чтение разных
размеров и выравниваний (границы 4 КиБ, конец 2 ГиБ, кадры 64…8192) во все каналы;
неверные запросы (13 видов); пачки регистров (до 256 операций, eth40_regs, смена IP и
порта); повтор REG (кэш, другой источник, дубль во время опроса); опрос и таймаут;
чужие кадры (IPv6, PAUSE, чужие MAC/IP/порт, широковещательный, контрольная сумма IP,
фрагмент, MAGIC, укороченный, tuser); дубли и перестановка записи, перезапрос чтения;
переполнение FIFO приёма и повтор; скорость. Результаты — `sim/eth40/out/`.

ПК: `tools/test_otpu_eth.py` (pytest, upstream venv): обмен C и Python с потерями,
дублями и перестановкой 3 %, ровно одно выполнение записи регистра, опрос и таймаут,
